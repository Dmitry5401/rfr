# Тестовые данные rfr-e2e

1. **Уникальность.** Имя и пароль берутся из `TestUser.unique()` (`RandomDataUtils`, префикс `rfr_`). Общие логины и повтор одного `TestUser` между тестами не используются.
2. **Владелец — дерево декораторов.** Корень — `UserFixture` из `UserRequest.fixture()`. Декоратор владеет `origin` и своими партнёрами: `friends`, `requesters`, `invitees`. Поля extension, статика и `ThreadLocal` пользователей не держат.
3. **Новое предусловие — новый декоратор.** Его добавляют композицией в `UserRequest.fixture()`, а не флагом в `SingleUserFixture` и не веткой в `UserExtension`.
4. **SQL только в объектах строк `data/db`.** `AuthAccount`, `ApiProfile`, `Friendship`, `Friendships`, `Invitations` читают `sql/` и реализуют `DbEntity`. В `jupiter`, в `data` вне `db` и в `test` SQL нет.
5. **Профиль API создаётся явно.** `SingleUserFixture.create()` вызывает `ApiProfile.create()` отдельно от `AuthAccount.create()`. Страна профиля берётся из справочника `country` (`code = 'ru'`), а не как побочный эффект учётки.
6. **Пул заранее заведённых пользователей — только там, где создать нельзя.** Обычный пользователь, друг и приглашённый создаются фикстурой и ею же закрываются. Готовый пользователь допустим лишь если `create()` эту строку получить не может.

## Формат ответа

Для новых данных: владелец, чем имя уникально, какой объект `data/db` пишет строку и почему это не пул. Без найденной причины изменений не предлагай.
